# ICML 2027: shared target evaluation and pruning tools

The research question is whether independently measured functional modularity
predicts specialist compressibility beyond baseline quality and other controls.
The framework implements baseline quality, component discovery/causal probes,
independent target-calibrated Wanda frontiers and organization diagnostics.
Offline tests validate engineering behavior and provide no evidence for the hypothesis.

## Run and inspect

```powershell
python experiments/icml2027/run_target_baseline.py --config configs/experiments/icml2027/target_baseline.json --validate-only
python experiments/icml2027/run_target_baseline.py --config configs/experiments/icml2027/target_baseline.json
```

Only the first command was checked on the local MMLU dataset during development.
The second loads a model and evaluates it. The example uses TinyLlama, CPU,
10 sampled validation records per domain and cached weights; this is a small
engineering configuration, not the planned 7–8B scientific pilot.

Config fields are validated, including unknown/misspelled keys. Dataset paths
are relative to the config file. Set `target.field` to `domain`, `language`,
`capability` or `task`, and `target.value` to an explicit dataset label. All
values of that field on the configured split are evaluated, so target and
non-target measurements come from the same run. Missing labels fail validation.
Old MC records still load for domain evaluation; missing languages are not
inferred. QA records also support the target abstraction, but this runner
evaluates MC only. Math/code generation tasks need separate evaluators.

Set `revision` to an immutable model commit for research runs. Both tokenizer
and model receive it. `local_files_only` defaults to true; downloading requires
an explicit false value. `max_records_per_value` may be null to use the whole
chosen split. Capped samples are seeded, drawn from ID-sorted records, and saved
by ID. Seeded selection does not promise bit-identical GPU inference.

Results go to `results/<experiment_name>/`, or `--results-root`. Existing folders,
including empty or failed runs, are rejected before model loading. Retry with a
new name. A run writes:

- `config.json`: resolved configuration.
- `manifest.json`: commit/dirty flag, versions, seed, input SHA-256, requested and
  resolved model revision (null when unavailable), actual device/dtype, evaluation
  definitions/counts and running/complete/failed status.
- `evaluation_records.json`: selected IDs, split, field/value and source.
- `candidate_scores.csv`, `decisions.csv`: detailed MC results using the legacy
  column schema, joined to target labels through selected record IDs.
- `metrics.json`: accuracy, correct-answer loss and margin per target-field value.
- `summary.md`: at most 40 lines; failures retain their error in the manifest.

## Measurement and split policy

Candidate scores and decisions reuse the existing MC evaluator without changing
the metric definitions. Prediction uses the highest **mean token log-probability**,
with choice order breaking ties. Accuracy weights examples equally; correct loss
is the mean negative token log-probability of the correct continuation; margin is
correct minus best incorrect mean token log-probability. `choice_text` and `letter`
are distinct protocols and must not be pooled without justification.

The complete dataset is audited before split filtering or sampling. Duplicate
IDs and normalized inputs shared across discovery/validation/test are rejected.
For MC, identity includes the question and the multiset of normalized options,
so reordered options cannot hide reuse and generic question stems alone do not
trigger errors. This does not detect paraphrases, shared facts, translated
equivalents or overlap in source passages; those need source-level audits.

Use discovery for component measurement/selection, validation to fix choices,
and test for the frozen final protocol. Passing this baseline preflight does not
enforce that later experiment decisions respected those roles.

`prompt_policy` explicitly selects legacy, plain base-model or native tokenizer
chat formatting; example configs use the native template. Instructions remain
English and prompt quality/multilingual controls still need scientific validation.
No conclusions about causal importance,
compressibility or multilingual competence follow from the offline random-init
tests or the example config.
